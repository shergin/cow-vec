# CowVec 2.0 Redesign: Two-Level Paged COW Vector

*2026-08-14. Motivated by a concrete workload; supersedes the arena-chain idea from the general assessment as the primary 2.0 direction.*

## Decision (2026-08-14)

Keep the `cow_vec` crate name and ship **both types in one crate**: the existing arena-based flat type stays `CowVec`; the new paged type is `PagedVec`. Rationale and plan:

- `PagedVec` is additive → ships in **1.5.0**, decoupled from the 2.0 breaking cleanups. Roadmap: 1.4.1 (provenance/UB fix) → 1.5.0 (`PagedVec`, traits, `alloc_extend`, iterator) → 2.0 (`CowVec` API breaks: `make_mut`, owned `pop`/`remove`).
- Positioning becomes "vectors optimized for O(1) clone — pick your divergence/access trade-off" (im-style multi-type crate). README gets a decision table: `CowVec` = 2-load access, O(n) divergence; `PagedVec` = 3-load access, page-granular divergence; `imbl` for many-edits/auto-reclaim.
- **Method parity, no shared trait** (std Vec/VecDeque precedent) — switching types should be a one-word change.
- `PagedVec<T, const PAGE_SIZE: usize = 1024>` — power-of-two pages → shift/mask indexing; page size is the tuning knob.
- **One storage backend first**: arena-backed pointer pages (matches workload + crate identity). Inline-`T` / `Arc<T>` variants deferred.
- Cost accepted: two unsafe engines. Mitigation: genericize/macro-ize the existing model-test suite so both types run identical tests, both under Miri in CI.

### Taxonomy: two axes, not three types

Considered and rejected: shipping the arena-chain as a third public type. The design space is a 2×2 grid of orthogonal axes:

- **Structure** (user-facing trade-off → public types): flat (`CowVec`, 2-load access, O(n) divergence) vs paged (`PagedVec`, 3-load access, page-granular divergence).
- **Value store** (no user-facing trade-off → internal engine): shared mutex arena vs arena-chain. Identical semantics, divergence cost, and leak profile; the chain is simply lock-free. A separate type would force a choice users can't reason about.

The arena-chain becomes shared internal infrastructure for both types: in `CowVec` it removes the mutex; in `PagedVec` it enables automatic per-page reclamation (keep-alive Arcs stored in the pages that reference each arena generation).

Caveat on "strictly better": under heavy branching with tiny per-branch allocation, many small arenas waste minimum-chunk capacity where one shared arena packs densely — mitigate with small initial chunk sizes.

Sequencing: `PagedVec` first (serves the driving workload), then the chain engine once the genericized test suite + Miri CI can validate it in both hosts. Chain is API-compatible (could be a 1.x minor for `CowVec`) but may bundle with 2.0 as a clean break.

## The driving workload

- One vector of **4M elements**.
- Every **~50ms**, a new version is derived where **~50 items are replaced**, chained version after version.
- Random **temporary branching** off versions (clone, mutate, discard).
- The churn set across generations is small — roughly **10k distinct hot elements** out of 4M.
- Priority: **best cache locality for accessing** the vector.

## Why the arena-chain redesign doesn't fit this workload

The arena-chain design (per-instance arenas + frozen keep-alive chain) removes allocation *locking*. At 50 replacements per 50ms, mutex traffic is ~1–2µs per generation — not a bottleneck. It fixes the wrong thing.

The dominant cost is the **flat pointer table**, which arena-chain keeps intact:

- `items` for 4M elements is a **32MB** pointer array.
- Every new version: clone → first `set` → `Arc::make_mut` → **full 32MB memcpy**.
- At 20 generations/sec: ~64MB of memory traffic per generation (read + write), ~1.3GB/s sustained.
- Every temporary branch that mutates pays another 32MB before being discarded.
- The ~1ms copy time is arguably tolerable; the worse effect is that streaming 64MB through the cache hierarchy twice per generation **evicts L1/L2/L3 every 50ms** — precisely when the hot 10k elements should stay resident.

Garbage behavior is identical in both flat designs: the newest version pins every ancestor's allocations (single shared arena or chain — same), accruing ~1,000 stale values/sec until compaction, and compacting a flat 4M vector is a stop-the-world O(4M) rebuild.

## The design: fixed-depth page table

A paged COW vector — a page-table, not a flat array and not a deep RRB tree:

```
root: Arc<Vec<Arc<Page>>>     // 4096 entries — 32KB, permanently cache-resident
Page: [element; 1024]          // 8KB of pointers, or values inline
```

### Cost profile for the driving workload

- **Per generation** (50 scattered replacements): COW the root (32KB) + ≤50 touched pages (8KB each) ≈ **~0.4MB copied instead of 32MB — ~75× less**. Same factor for every temporary branch. Nothing large enough to disturb the cache streams through.
- **Random access**: index-split → root (always warm; it's 32KB, lives in L2) → page → value. Effectively one extra dependent load vs the flat design — fixed depth 2, vs ~5 levels for a 4M-element RRB tree.
- **Iteration**: linear within 8KB pages; values mostly contiguous when bulk-loaded.
- **Compaction becomes incremental**: re-localize k pages per tick with bounded pause. The flat design structurally cannot do this.
- **Hot set**: the ~10k churned values scatter across generation allocations over time, but 10k hot values are cache-resident by virtue of being hot; page-granular compaction re-packs them.

Page size is a tuning knob: larger pages → cheaper indexing and better iteration, more copied per touched page; smaller pages → cheaper divergence, bigger root.

### Element storage inside pages — decision rule

| Element storage | Best when | Trade-off |
|---|---|---|
| `T` inline | `T` small, `Clone` cheap | Best locality, zero unsafe, no arena; page COW clones 1024 elements |
| `Arc<T>` | pragmatic default | All-safe, automatic reclaim; page COW = 1024 atomic incs (~50k/gen ≈ 0.1ms — fine) |
| `*const T` + arena | `T` expensive, max perf | Pure 8KB memcpy per page, bump alloc; needs compaction machinery |

### Where arena-chain returns as a complement

If using the arena-backed element storage: per-generation arenas whose keep-alive `Arc`s live **in the pages that reference them**, not in one global chain. An old generation's ~50 values free automatically once every page referencing them has been COW'd away — which converges for a bounded churn set (~10k hot elements). That is the version of arena-chain that earns its place: as the value store behind pages, not as a standalone fix. Each page holds a small dedup'd set of arena-generation `Arc`s alongside its pointers.

## Caveat: benchmark `imbl` first

`imbl::Vector<T>` on this exact loop copies ~100–200KB of tree nodes per 50-change generation — the same order as the paged design — with automatic reclamation and zero unsafe. What the custom design buys over it is exactly the stated priority:

- fixed 2-level depth (~3 dependent loads vs ~5 for a 4M RRB tree);
- 8KB-contiguous iteration.

If an `imbl` benchmark is fast enough, stop there. If access latency matters, this is the cow_vec 2.0 positioning — a genuinely unoccupied niche between `Arc<Vec<T>>` and RRB trees:

> **Page-table persistent vector: O(1) clone, depth-2 access, pointer-only divergence.**

## Cost comparison per generation (4M elements, 50 replacements)

| Design | Bytes copied per divergence | Access depth | Reclaim |
|---|---|---|---|
| Flat CowVec 1.x (and arena-chain) | 32MB | 2 loads | stop-the-world compaction |
| Paged (this doc) | ~0.4MB | 3 loads (root always warm) | incremental, per-page |
| `imbl::Vector` | ~0.1–0.2MB | ~5 loads | automatic |
| `Arc<Vec<T>>` + `make_mut` | 4M × `Clone` of `T` | 1 load | automatic |
